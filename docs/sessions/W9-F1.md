## Summary

- A guardian void (`RoundRefunded` reason 4) tells its Stakes entrants again: the scheduler tick's new
  step 7 sweeps the daily rounds whose Stakes mode became `voided` in the last 10 minutes and calls
  `enqueueVoidOutcomes` (owner decision, option a; as an indexer handler it broke the poll's D1
  budget, W9-D open issue 1). A round whose Stakes outcomes already reached `notification_log` is left
  out, so the usual cost is one query a tick.
- **R2:** a Stakes refund the contract proposed first is the game day's `outcome` at the proposal only
  when it is the user's first mode outcome, and is told as `refunded` when it becomes final. The
  `outcome` payload carries `provisional`, and the post-final hook asks whether a proposal preceded
  the refund (`claims_open_at`) instead of reading the reason alone.
- **R3:** every `notification_log` claim is fenced by its lease, so a batch stalled past 60 s can't
  record a channel, finish the key or release the lease of the delivery that reclaimed it; the
  consumer reads the clock per message; and channel requests are aborted after 10 s.
- **R4:** an outcome is rendered from the account the payload names and delivered to the account it
  joined, so a merge no longer drops it as `notify_unrenderable`.
- The owner's decisions: a deleted owner's room passes to the oldest active member, else the oldest
  suspended one (never a merged or deleted account; with neither the room closes); `memberCount` is
  the cap's count; `GET /rounds` shows a closed round's pending mode as `revealing` past beacon time.

## Spec issues

1. **"Identity and personhood" › Merging accounts says nothing about notification state** (R4's
   neighbour, for W10-Z). A merge re-points neither `push_subscriptions` nor `notification_prefs`, so
   a device subscribed only under the merged-away account is never used again, and the prefs the user
   set there are silently replaced by the kept account's. Recommendation: say that a merge moves both
   — `push_subscriptions` with an upsert on its unique `endpoint` (W9-A's open issue), and
   `notification_prefs` only for (channel, event) pairs the kept account hasn't set, so its own
   choices still win.
2. **A guardian void before close takes the game day's `outcome` key** ("Notifications", the `outcome`
   row: "At the user's first mode outcome at the reveal"). The sweep enqueues `outcome` for a Stakes
   mode voided hours before `closesAt`, as the decision and `enqueueVoidOutcomes` prescribe; the Free
   mode then reveals later the same game day and is app-only, so a player who entered both modes never
   hears their Free result. Recommendation: tell a void that happens before the round's beacon time
   under `refunded:{roundId}:{mode}:{userId}` (the `refunded` row already covers a refund that isn't
   the day's first outcome), leaving the `outcome` key for the reveal. Not changed here: it would
   depart from the decided behaviour.

## Open issues

- **The sweep's window is stateless** (`VOID_SWEEP_WINDOW_MS`, 10 min; no migration this session, so
  no cursor). A void whose notices never reach `notification_log` within the window — the scheduler
  down for more than 10 minutes, or the notify consumer failing throughout — is never swept again. A
  cursor (a `config` row or a column on `round_modes`) would close that gap. Owner: W13-B, which
  already lists "the tick's new sweep".
- **`notification_log.source` has no index**, so while a void sits inside the window each tick scans
  `notification_log` for the sweep's `NOT EXISTS`. Harmless at today's size and gone once W13-A prunes
  the table (an index can come with that migration).
- **`notify_lease_lost`** (a batch that ran past its 60 s lease) is a warn log with no alert; if it
  ever fires, a duplicate notification was sent. W13-A could alert on it.
- A guardian void of a **room** round's Stakes mode still tells nobody: room results are app-only
  (spec "Notifications"), so the sweep filters `kind = 'daily'`, as `enqueueVoidOutcomes` does.
