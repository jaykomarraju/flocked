## Summary

- **H1 (the tick):** `driveCancellations` runs before any per-round work (and once more at the end only if step 4 abandoned a `createRound`, so it is still replaced in the same tick); the daily rounds are locked and visited first; a tick locks at most `ROOM_LOCKS_PER_TICK` (50) room rounds and visits a page of `ROOM_ROUNDS_PER_TICK` (50) live room rounds that rotates every minute. Open room rounds are skipped unless their Free lock leaf is pending or they are past close (a stalled alarm). With 300 rooms a tick costs at most 423 D1 statements (was over 1,000).
- **H1 (the cap):** at most `ROOM_MAX_OWNED` (10) open rooms per owner; `POST /rooms` answers 409 `conflict` past it, read inside the insert, so concurrent creates hold it.
- **M1, L1:** the lock's `UPDATE` and the quiet room-round close apply only while `rounds.question_id` is still the value read (`IS ?`) and the picked question still has the status read; a stale attempt re-reads the round and retries (3 attempts, then it throws and the next tick retries). The no-round-day close also requires the `question_id` read. Assign requires a `scheduled` round (read and batch guard). A room question's "lock still ahead" check uses the clock after moderation.
- **M2:** `limitUser('writes')` on `POST /rooms/:id/questions`; `refuseOverQuota` is exported from `questions/submit.ts` and the copy is gone. **M3:** the visit grant only for an active session user (as the daily grant). **L2:** `editQuestion` refuses room questions (`conflict`, the existing `refuseRoomQuestion`).
- **L3:** the room and member inserts require `users.status = 'active'` in SQL; a refused room insert fails the owner row's NOT NULL (its user ID comes from the inserted room), rolling the batch back. Both answer 403 `account_suspended`.
- **Decisions:** the 50-member cap counts only non-deleted members; the hand-over prefers the oldest active member, else the oldest non-deleted one (L4).
