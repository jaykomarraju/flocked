## Deviations

- **Changed tests.**
  - `identity/merge.test.ts` "keeps a waiting raise…" asserted the old rule. It is now "keeps only the waiting raise…": the `row(5)` vs `row(50, 40)` case expects no raise, and an equal-caps test was added.
  - In `identity/merge.test.ts` "moves everything…", the fixture's raise now sits on the side whose cap is in force. The expected state is unchanged.
  - `ws/snapshot.test.ts` DO-5: a reconnect at beacon time now gets `['state']` with status `revealing`, instead of `state` then `revealing`.
  - `identity/delete.test.ts` "refused while…": the expired ticket is marked used. With no indexer position, R8 makes any unused ticket block deletion.
  - `round-do/entries.test.ts`: a non-member gets `not_found` (optional item b).
  - No test was skipped or deleted.
- **`src/auth/profile.ts`** is outside the owned list. `buildMe` builds `/me`'s limits, so R3 adds `maxDailyCap` there: one statement in its batch.
- **R6.** The `OutcomeProposed` handler now commits its own D1 batch, then calls the RoundDO. Previously it returned statements to the dispatcher. Every statement is conditional, so a replay changes nothing and the RoundDO ignores the repeat. Neither the dispatcher nor `indexer/types.ts` changed; the `EventHandler` doc comment there still describes only the return-statements pattern.
- **R13.** Only the veto-removal path restores by `seq`. The `RoundRefunded` reason-5 removal still restores by time: the veto's own removal, dispatched next, puts the record back.
- **W6-F1's R4 test** in `settlement/stakes-review.test.ts` uses `round_modes.bundle_hash = 'untouched'` as a marker. Since R15, `applyStakes` never writes that column, so the assertion is vacuous. Its entries marker still catches R4.
- **Optional item not done:** telling connected viewers when a Stakes proposal is reorged out. It needs either a `ModeResult` for "open again" (`do/types.ts`, pinned) or a post-commit hook in the dispatcher (not owned), and viewers already get the right state on reconnect. It stays open (below).

## Spec issues

- "Identity and personhood" › Merging accounts refuses a merge when either account holds a live Stakes ticket, but `merge.ts` (W7-B) carries tickets as well. Both together are consistent; recommend keeping both and noting that tickets carry only for the re-verification path.
- "API" › Reveal gating says the indexer's `revealed` "may precede its D1 batch by milliseconds". Since R6 it follows the commit. Recommend: "is sent after its D1 batch commits".
- "Real-time and the reveal": a WebSocket `state` past beacon time shows `revealing` for a closed round's pending mode (R1), while `GET /rounds/:id` still says `pending`. Recommend the same rule for `GET /rounds/:id` (`read/rounds.ts`, W8-B's this wave).

## Open issues

- **`GET /rounds/:id` past beacon time** still says `pending` (above): W8-D or W9-C, in `read/rounds.ts`.
- **A reorged-out Stakes proposal** doesn't reach connected viewers until they reconnect: the optional item, now W9-C or W13-B.
- **The `RoundRefunded` handler** still calls the RoundDO before its D1 commit. Only the Stakes `revealed` was in R6's scope; the same pattern applies (W13-B).
- **R16 path.** A proposal whose root doesn't match stays `revealing` and alerts. A later `RoundFinalized` would still settle it from the record, as the `bundleHash` mismatch path does, so the guardian has to act on the alert.
- **R8 on a fresh deployment.** With no indexer position, `indexedThroughSec` is null, so every unused ticket blocks deletion until the indexer has a stamped position.
- **R5 duplicates.** A timed-out event is retried, so a late shard answer can deliver it twice. Clients must treat events idempotently (W9-C).
- **R12 timing.** The callback refuses a suspended account after the Coinbase token exchange. Refusing before it needs a change in `personhood/flow.ts`.
- **R2 guard abort.** If the limits or tombstone change mid-callback, the guard aborts and the callback answers `unavailable` with its OAuth state spent; the user starts again.
- **`PUT /me/limits`** (`api/limits.ts`) doesn't carry `maxDailyCap`; only `/me` does (W12-B can add it).
- **A noisy alert.** A veto re-mined within one poll raises `stakes_veto_unexpected` when it is re-added.

## Notes for D and Z

- **Migration `0020_indexer_block_timestamp.sql`.** Adds `indexer_state.last_block_timestamp` (Unix seconds, CHECK `>= 0` or NULL). The indexer writes it with every position advance; rows written before the migration are NULL until the next advance, and `indexedThroughSec` falls back to W6-F1's bound for them. It applies under `node:sqlite` (`e2e/tests/indexer-reorg.test.ts`). Wave 9's migrations start at `0021`.
- **Config key** `limits.stakes.maxDailyCap`: USDC base units, a decimal string or a safe integer. A missing or invalid value, or one above the default, reads as `DEFAULT_MAX_DAILY_STAKE_CAP` (1,000 USDC). The default and the key are in `packages/shared/src/config.ts` (`MAX_DAILY_STAKE_CAP_KEY`). No seed is needed.
